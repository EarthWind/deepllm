# 02 · 数据与分词：文字怎样变成训练样本

[← 上一章](01-全局地图.md) · [返回目录](README.md) · [下一章 →](03-模型内部.md)

## 1. 收集文本只是开始

预训练材料可以包含网页、书籍、论文、代码和结构化数据转写等。实际可用性取决于来源质量、授权、隐私和任务需要，不能简单按体积越大越好排序。

一条可审计的数据流水线通常包括：

1. **记录来源**：原始地址、采集时间、许可、版本、语言、领域。
2. **解析正文**：去掉导航、重复页脚与损坏内容；保留代码缩进和有意义的结构。
3. **过滤与去重**：处理垃圾文本、敏感信息和重复材料；近似去重识别轻微改写的副本。
4. **分组切分**：按文档、来源、用户或时间划分训练、验证和测试，避免相关片段跨集合。
5. **分词与组样本**：转成 token，按照长度、边界和训练目标构造序列。
6. **统计与抽检**：检查语言比例、长度分布、重复率及过滤误杀，保存可复现版本。

去重可以在切分前进行；切分后还应做跨集合近似重复检查。若先随机切段再分集合，同一文章的相邻段落可能同时出现在训练集和测试集，评测就会过于乐观。

## 2. Token 不是固定的“一个字”或“一个词”

Tokenizer 把文本变成离散 ID。常见方法包括 BPE 和 Unigram；不同模型的词表、规范化与字节处理规则不同。

```text
原文：我想申请 GPU。
示意切分：[我] [想] [申请] [ GPU] [。]
示意 ID：[31, 82, 906, 4821, 7]
```

这不是任何具体 tokenizer 的真实输出。空格、标点、中文、罕见词和代码都可能产生不同的切分。上下文窗口和计费常以 token 计量，因此不能用字符数直接代替。

Tokenizer 需要和训练时保持兼容。随意更换 tokenizer 后，同一个 ID 可能代表另一段文本，Embedding 与输出头也可能不匹配。训练自己的 tokenizer 时，应使用训练分区的数据，避免测试集信息泄漏。

## 3. 下一个 token 的标签怎样构造

对序列 `x₁, x₂, …, xₜ`，模型学习从前缀预测后续 token：

```text
输入位置：   我      想      申请      GPU
预测标签：   想      申请    GPU       。
可见范围：   我      我想    我想申请  我想申请 GPU
```

有些框架由数据管道错位标签，有些在模型内部完成；不能两边各错位一次。

**因果注意力掩码**阻止某个位置读取未来 token。训练可以在同一次前向计算中并行算出多个位置的预测，但每个位置仍然只能使用自己的前缀。

**损失掩码**决定哪些位置计入训练目标，例如忽略 padding，或在 SFT 中只对助手回答计损失。它与注意力掩码是不同的东西：不计损失的用户问题仍应作为上下文被读取。

## 4. 长文怎样装进有限窗口

- **截断**：简单，但可能丢失结论、答案或关键指令。
- **分块**：保留局部内容，需考虑段落边界与跨块依赖。
- **Packing**：把多个短样本装进一个窗口，提高有效 token 比例。

Packing 需要明确样本边界和注意力策略。只有 EOS 分隔符，并不自动阻断跨样本注意力；是否隔离，要看实现和目标。

RAG 的文档分块与训练分块服务于不同目标。前者希望检索后提供足够完整的证据，后者关注训练窗口利用率与学习目标，不能直接照搬同一长度。

## 5. 一个指令样本包含什么

```json
{
  "messages": [
    {"role": "user", "content": "请根据给定制度说明 GPU 申请步骤。"},
    {"role": "assistant", "content": "先填写申请单，再由负责人审批……"}
  ]
}
```

这只是数据交换结构。训练前还要通过聊天模板序列化为 token，加入角色边界和结束标记，并构造损失掩码。训练和部署模板不一致，可能导致角色混淆、无法停止或格式异常。

本章产物不是“一个大文本文件”，而是**有来源、版本、划分、tokenizer 与构造规则的数据集**。

延伸阅读：[SentencePiece](https://arxiv.org/abs/1808.06226) 介绍可直接处理原始文本的分词工具与子词模型；具体数据管道仍需按任务设计。

# 08 · 评测与迭代：怎样知道系统变好了

[← 上一章](07-RAG与工具应用.md) · [返回目录](README.md)

## 1. 评测贯穿全程

数据进入训练前要检查质量；训练过程中要看验证损失和能力；部署前要测服务；应用上线后要持续观察真实任务。最后才补一份测试题，往往无法区分问题出在哪一层。

内部助手的目标可以写成：“有权限的新同事提出申请问题时，能依据现行制度完整说明步骤，并给出可验证的引用；材料不足时说明缺口。”这比“回答看起来专业”更容易验收。

## 2. 建一份独立、有代表性的测试集

每个案例至少保存：问题、用户角色、所需文档版本、应包含的事实、可接受答案边界，以及禁止泄漏或执行的内容。覆盖常见问题、多轮追问、歧义、无答案、旧版冲突和越权访问。

训练数据、调提示用的开发集和最终测试集应区分。测试集一旦反复用于选参数，就已经承担了开发集的角色，应补充独立测试。按来源、用户或时间分组，防止同一材料的改写跨集合污染结果。

## 3. 分层指标比一个总分更有用

| 层次 | 示例指标 | 它没有单独证明什么 |
| --- | --- | --- |
| 基础模型 | 验证损失、领域题正确率 | 不等于企业任务成功率 |
| 检索 | Recall@k、排序质量 | 命中不代表模型一定采用 |
| 答案 | 事实正确、完整、证据支持比例 | 表达流畅不等于有依据 |
| 引用 | 来源存在、定位正确、支持断言 | 链接能打开不代表支持内容 |
| 工具 | 参数正确、权限遵守、执行成功 | 生成了调用 JSON 不等于执行成功 |
| 服务 | TTFT、p95 延迟、错误率、成本 | 平均值可能掩盖长尾问题 |
| 业务 | 任务完成率、人工转接、纠错比例 | 满意度可能受界面与用户群影响 |

例如，若 100 道问题中，80 道在前 k 条检索结果中找到了至少一条标注相关证据，可以报告“问题级 hit@k = 80%”。若题目需要多条证据，严格的 Recall@k 应按召回的相关证据数除以标注相关证据总数计算，并说明微平均或宏平均口径。

自动评测适合大规模回归，但模型裁判可能存在位置偏差、风格偏好和自我偏好。应使用明确量表、打乱顺序、人工抽检与一致性检查。代码类任务可运行测试，但测试本身也可能覆盖不足。

## 4. 一次改动怎样做可信比较

1. 冻结基线：记录权重、模板、索引、检索参数和推理设置。
2. 明确假设：例如“按章节分块能减少制度例外条款遗漏”。
3. 控制变化：先比较分块策略，避免同时替换模型和重排器造成归因困难。
4. 在相同案例上配对比较：报告样本量、改善和退化案例，以及适合任务的不确定性估计。
5. 检查成本与回归：正确率上升，是否伴随延迟、泄漏或工具误操作增加？
6. 小流量发布与监控：满足上线条件后逐步扩大，保留旧版本以便回滚。

不要在看完结果后只挑有利子集。业务是否接受某种权衡，应在发布前明确。

## 5. 按故障位置选择下一步

- **资料缺失或过时**：先修文档同步、版本与索引。
- **相关材料没召回**：改查询、分块、检索或重排。
- **材料进了上下文但被忽略**：检查模板、位置、长度和任务示例，再考虑模型适配。
- **格式经常错误**：检查约束解码、解析器、模板和针对性 SFT 的收益。
- **工具参数正确但执行失败**：检查接口、授权、超时和运行状态。
- **速度慢或显存不足**：按 prefill、decode、排队、检索与工具耗时分别定位。

这条反馈链最终回到生命周期起点，但生产日志不能未经审查就直接进入训练集。需要处理隐私、授权、低质量反馈和测试集隔离，数据迭代也要版本化。

## 6. 一个可复现的最小实践

不需要先训练大模型，也能走通应用流程：

1. 整理一小组有版本的制度文档，建立含无答案和越权案例的独立测试集。
2. 选用现成对话模型，保存模板和参数，建立无检索基线。
3. 接入检索，记录每题候选、最终上下文、回答和引用。
4. 加一个只读状态查询工具，验证成功、无权限、超时三条路径。
5. 比较任务正确率、引用支持情况、延迟与成本，整理具体失败案例。
6. 根据失败原因决定修数据、修检索、调提示，还是开展微调实验。

完成后，你应能回答：**模型学到了什么、这次请求看到了什么、系统执行了什么，以及结果为什么可信。**
